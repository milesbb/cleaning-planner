# Web — Claude Context

## README

`README.md` at the repo root is the developer setup guide. If your changes affect anything it documents — stack choices, env vars, CI/CD behaviour, or setup steps — update `README.md` to match.

Next.js App Router, built as a **static export** (`output: 'export'`, `trailingSlash: true`): the files in `out/` are the website on Vercel **and** the UI inside the iOS and Android apps (`apps/mobile`). Mobile-first, and every screen must work from 320px to 1920px wide.

## Static export — non-negotiable rules

- No server-only features: no route handlers, server actions, middleware, `cookies()`/`headers()`, or data fetching on the server. All data comes from the API at runtime in the browser.
- Pages that show a record read its id from the query string with `readRecordId` (`/job?id=…`), never from a dynamic route segment, because the export can't know users' ids.
- Metadata routes (`manifest.ts` and similar) declare `export const dynamic = 'force-static'`.
- Images use `next/image` with `unoptimized` (set in `next.config.ts`); there is no image server.
- **Content-Security-Policy**: `npm run build` runs `scripts/apply-content-security-policy.ts` after `next build`. It hashes each page's inline scripts and writes a strict policy into that page's `<head>` (only our files, those exact scripts, our API and Cognito). Never add inline event handlers, third-party scripts or `eval`. ESLint bans `dangerouslySetInnerHTML` and `eval`. Other security headers (HSTS, no framing, `nosniff`, referrer and permissions policies) are in `vercel.json`, with tests in `scripts/vercel-headers.test.ts`. `vercel.json` also sets `framework: null`, `buildCommand: npm run build` and `outputDirectory: out`: Vercel's Next.js preset would serve its own build output and drop the policy (tested in `scripts/vercel-build.test.ts`). Never switch the project back to the Next.js preset in the Vercel dashboard.
- **Service worker**: `npm run build` then runs `src/service-worker/build-service-worker.ts`, which bundles `service-worker.ts` with esbuild and lets Serwist's `injectManifest` precache every page, route-data `.txt` file, script, style, font and icon in `out/` (`build-settings.ts`), writing `out/sw.js`. The worker serves those files cache-first (any query and a missing closing slash still find the page, `page-file-urls.ts`), waits for open pages to close before a new version takes over, shows pushes (`reminder-notification.ts`) and opens the app from a tap (`open-from-notification.ts`). `useServiceWorker` in `AppProviders` registers it on the built site only, never under `next dev`. Web only: the iOS and Android apps use native push and their bundled files. Playwright blocks service workers (`serviceWorkers: 'block'`), because WebKit can't fake the backend for a page one controls; only `e2e/offline.spec.ts` allows it.
- **Review pages** (`/dev/components`, `/dev/shell`) are `page.dev.tsx` files. `next.config.ts` only treats `.dev.tsx` as pages when `src/lib/dev-pages.ts` allows it: locally, on Vercel previews, and in the e2e build (`INCLUDE_DEV_PAGES=true`), never on the live site. Add every new component to `/dev/components` in all its states.
- **JavaScript budget**: `npm run check:bundle-size` (PR checks, for PRs that change `apps/web`, `packages/schedule`, `packages/contracts` or the npm manifests, and release checks) fails a page whose first load is over 220 KB gzipped or has over 60 KB of its own JavaScript (`noModule` polyfills don't count; modern browsers skip them). Keep large libraries out of the first load: import them dynamically when first needed, as Amplify is, and open sheets through `LazySheet` so the dialog and each sheet's form load on first tap.
- Tests run against the exported files: `npm run start` serves `out/` with `serve` (on `PORT`, default 3000), and Playwright and Lighthouse use it in CI.

## Rules

- **Scheduling logic lives in `@cleaning-planner/schedule`.** Never compute due dates or intervals in a component; import from the package (`@cleaning-planner/schedule/next-due`).
- Use shadcn/ui components (`npx shadcn add <component>`, into `src/components/ui/`) before writing custom UI elements. The first `shadcn add` also creates `src/lib/utils.ts` with its `cn()` class merger: keep that name, because generated components import it. It is the one exception to the naming rules.
- Tailwind only for styling — no CSS modules, no inline style objects. Use the Wall chart tokens (`bg-paper`, `bg-card`, `text-ink`, `bg-kitchen`…`bg-whole-home`, `bg-late`, `shadow-hard`, `rounded-card`, `font-display`), never raw hex. A new colour goes into both palettes in `design-tokens.ts` and `globals.css`.
- Text is always `text-ink` (or `text-card` on an ink background); there is no grey text, because it fails contrast on the room colours.
- Never disable pinch-zoom (`maximumScale` / `userScalable`) in the viewport.
- Respect safe areas (`env(safe-area-inset-*)`) — the app runs full-screen from the iOS home screen.

## Component structure

- A page file (`page.tsx`) handles data fetching and layout only. Visual sections go into named child components in the same directory.
- Each component does one thing. Name components after what they display (`TaskRow`, not `Row`).

## Responsive design — non-negotiable rules

**Every UI must work on mobile (all screen sizes) and laptop. There are no exceptions.**

- Mobile-first; layer up with `sm:` / `md:` / `lg:`.
- Touch targets at least 44×44px. No hover-only interactions.
- Before marking any UI task complete, check it at a narrow mobile viewport and a laptop viewport. The app is light-only for now; dark mode is a later item in `docs/PLAN.md`.

## Test-driven development — non-negotiable rules

1. Write a failing test that specifies the expected behaviour.
2. Write the minimum code to make it pass.
3. Refactor — keep the test green.

Never write implementation code that is not covered by a test.

## Tests

- Vitest + React Testing Library, jsdom. Test files sit next to the source (`page.tsx` → `page.test.tsx`). Run `npm test` from `apps/web`.
- Test user-facing behaviour (roles, text, callbacks), not internal state.
- **Every component test file includes an axe check** as the first test in the first rendering `describe`:
  ```ts
  import { axe } from 'vitest-axe';
  it('has no accessibility violations', async () => {
    const { container } = render(<Component />);
    expect(await axe(container)).toHaveNoViolations();
  });
  ```
  The `toHaveNoViolations` matcher is defined in `src/test/setup.ts` (the one bundled with `vitest-axe` is incompatible with current Vitest). For open Radix portals/dialogs, pass `document.body` instead of `container`.
- **Every screen size (Playwright viewport matrix):** every screen gets its own `e2e/<screen>.viewports.spec.ts` (never a shared one) that calls `testAtEveryViewport(name, path)` from `e2e/support/viewport-matrix.ts`. It loads the screen at 10 sizes from a 320px phone to a 1920px desktop (including a phone in landscape) and fails on sideways scrolling, touch targets under 44px (links inside sentences excepted) or axe violations, attaching a screenshot of each size to the report. These run in their own `viewports` project.
- **E2E (Playwright):** every new page or user flow gets a spec in `e2e/` covering the happy path and at least one error/edge case. Specs run on three projects: `desktop` (Chrome), `android` (Pixel 7) and `iphone` (iPhone 15, WebKit). Run `npm run test:e2e` from `apps/web` (uses `next dev` locally; CI runs against `npm run start` after a build). The server listens on `E2E_PORT` (default 3000; `scripts/e2e-port.ts` rejects anything but a whole number from 1024 to 65535), passed to `next dev` and `serve` as `PORT`, so each worktree can run e2e on its own port.

## Types

- All exported function return types explicit (ESLint enforces explicit return types everywhere).
- No `any`; `unknown` only when immediately narrowed. No type assertions (`assertionStyle: never` is enforced).
- `interface` for object shapes, `type` for unions.
